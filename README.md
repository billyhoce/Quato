# Quato

An LLM-powered agent that converts plain-text trading strategy ideas into runnable [QuantRocket Zipline](https://www.quantrocket.com/docs/api/zipline/) backtests and manages their execution.

## Overview

Quato exposes a REST API that a frontend can interact with. A user describes a strategy in natural language, the agent generates valid Zipline Python code, and the user can submit it for backtesting. Backtests are queued in Redis and executed against a QuantRocket cloud instance one at a time in FIFO order, regardless of how many server instances are running.

### What you can do

- Chat with the agent to generate a Zipline strategy
- View the current strategy code for your session
- Revise the strategy through follow-up messages
- Submit the strategy for backtesting
- Poll for backtest status and results
- View the backtest history for your session

### Tech stack

| Concern | Technology |
|---|---|
| API server | FastAPI |
| LLM | Google Gemini 2.5 Flash via LangChain |
| Agent framework | LangGraph |
| Zipline tools | MCP server (`mcp_server/`) |
| Session & strategy state | Redis |
| Conversation history | Redis (LangGraph `AsyncRedisSaver`) |
| Backtest queue & locking | Redis |
| Backtest execution | QuantRocket / Zipline |
| Strategy delivery to QuantRocket | GitHub (commit → pull workflow) |
| Backtest result storage | MinIO (S3-compatible object store) |

## Prerequisites

- Python 3.12+
- Docker (for local Redis and MinIO)
- A running QuantRocket instance with `HOUSTON_URL` accessible
- A GitHub repository used as the strategy file bridge
- A Google AI API key (Gemini)

## Local development setup

### 1. Clone the repo

```bash
git clone https://github.com/billyhoce/Quato.git
cd Quato
```

### 2. Install dependencies

```bash
pip install -e .
```

### 3. Start Redis and MinIO

```bash
docker compose up -d
```

Both Redis and MinIO start together. Data is persisted in named Docker volumes (`redis_data`, `minio_data`) so it survives restarts. To wipe all state and start fresh:

```bash
docker compose down -v
```

The MinIO web console is available at [http://localhost:9001](http://localhost:9001) (default credentials: `minioadmin` / `minioadmin`). The S3-compatible API is on port `9000`.

### 4. Configure environment variables

Create a `.env` file in the project root:

```bash
# Google Gemini
GOOGLE_API_KEY=your_google_api_key

# QuantRocket
HOUSTON_URL=http://your-quantrocket-host
HOUSTON_USERNAME=your_username        # optional, if auth is enabled
HOUSTON_PASSWORD=your_password        # optional, if auth is enabled

# GitHub (strategy file bridge to QuantRocket)
GITHUB_TOKEN=your_github_token
GITHUB_USERNAME=your_github_username
REPO_PATH=your_username/your_repo     # e.g. billyhoce/quato-strategies

# Redis
REDIS_URL=redis://localhost:6379

# Object store (MinIO for local dev; swap endpoint for AWS S3 in production)
OBJECT_STORE_ENDPOINT=http://localhost:9000
OBJECT_STORE_ACCESS_KEY=minioadmin
OBJECT_STORE_SECRET_KEY=minioadmin
OBJECT_STORE_BUCKET=quato-backtests
OBJECT_STORE_REGION=us-east-1

# LangSmith tracing (optional)
LANGCHAIN_TRACING_V2=true
LANGCHAIN_API_KEY=your_langsmith_api_key
LANGCHAIN_PROJECT=quato
```

### 5. Run the server

```bash
uvicorn api.main:app --reload
```

## API reference

All stateful endpoints require an `X-Session-ID` header. The session ID must be generated by the client (a UUID) and persisted across requests (e.g. in `localStorage`). The server will return `400` if it is missing.

### Chat

```
POST /api/chat
X-Session-ID: <uuid>

{ "message": "Create a momentum strategy using the daily bundle" }
```

The agent responds with an explanation and, if it generated or revised code, the updated strategy is stored in Redis for the session.

### View current strategy

```
GET /api/strategy/current
X-Session-ID: <uuid>
```

### Start a backtest

```
POST /api/backtest
X-Session-ID: <uuid>

{
  "bundle":       "usstock-learn-1d",
  "start_date":   "2023-01-01",
  "end_date":     "2023-12-31",
  "capital_base": 100000
}
```

`bundle` defaults to `"usstock-learn-1d"` if omitted. Returns a `task_id` immediately — the backtest is placed in the Redis FIFO queue.

### Poll backtest status / results

```
GET /api/backtest/{task_id}
```

Possible `status` values: `queued` → `running` → `complete` / `failed`

On completion the response includes summary metrics extracted from the results CSV:

```json
{
  "task_id": "...",
  "status": "complete",
  "success": true,
  "total_return": 0.142,
  "sharpe_ratio": 1.23,
  "max_drawdown": -0.08,
  "execution_time": 42.1,
  "csv_object_key": "backtests/<task_id>/results.csv"
}
```

### Download backtest results CSV

```
GET /api/backtest/{task_id}/download
```

Returns a pre-signed URL valid for 1 hour that allows direct download of the full backtest results CSV from the object store — suitable for passing to `pandas.read_csv()` or a browser download link. No further authentication is required to use the URL.

```json
{
  "download_url": "http://localhost:9000/quato-backtests/backtests/<task_id>/results.csv?...",
  "expires_in": 3600
}
```

### Backtest history

```
GET /api/backtest/history
X-Session-ID: <uuid>
```

Returns all backtest tasks for the session, most recent first.

### Health check

```
GET /health
```

## Architecture

### Session identity

The `X-Session-ID` header is the sole user identity mechanism. The client generates a UUID on first load and sends it with every request. All per-user state (strategy code, conversation history, turn count, backtest history) is keyed by this ID in Redis, so any server instance can serve any request.

### Redis key schema

| Key | Type | Content |
|---|---|---|
| `strategy:{session_id}` | String | Current strategy Python code |
| `session:turns:{session_id}` | Integer | Conversation turn counter |
| `backtest:queue` | List | FIFO queue of pending `task_id`s |
| `backtest:task:{task_id}` | Hash | Task status, config, metrics, object store key |
| `session:{session_id}:tasks` | Set | All `task_id`s for a session |
| `backtest:lock` | String | Distributed lock (holds `task_id` of running backtest) |
| LangGraph keys | Various | Conversation checkpoint data (managed by `AsyncRedisSaver`) |

### Backtest execution flow

1. `POST /api/backtest` creates a task hash in Redis and pushes the `task_id` onto the queue
2. A `BacktestWorker` on one of the server instances dequeues the task
3. The worker acquires a distributed Redis lock (only one backtest runs globally at a time)
4. Strategy code is uploaded to GitHub and pulled into QuantRocket via `/codeload/repo`
5. `zipline.backtest()` runs on the QuantRocket instance (blocking, executed in a thread pool)
6. The results CSV is uploaded to the object store (MinIO / S3); summary metrics (`total_return`, `sharpe_ratio`, `max_drawdown`) are extracted and written to the task hash; lock is released
7. Local strategy and results files are deleted immediately after upload

### Multi-instance coordination

All instances share the same Redis. The distributed lock (`backtest:lock`) ensures only one backtest runs at a time across the fleet. Workers check for an active lock before dequeuing, minimising unnecessary churn. Lock release is atomic via a Lua script to prevent TOCTOU races.

On startup, each instance checks for orphaned `running` tasks (server crashed mid-backtest) and marks them `failed` — but only if no lock is currently held, so a healthy peer's active backtest is never disrupted. A periodic cleanup task (every 15 minutes) catches any tasks that outlive the lock TTL.

### Failure recovery

| Scenario | Recovery mechanism |
|---|---|
| Server crashes mid-backtest, other servers healthy | Lock expires after 3 h; periodic cleanup marks task failed |
| Server crashes, no other servers running | Startup recovery on next server boot marks task failed |
| All servers crash | Same as above — first server to restart cleans up |
| Server restarts while peer holds lock | Startup recovery skips cleanup (lock held); peer completes normally |

If your backtests regularly take longer than 3 hours, increase `BACKTEST_LOCK_TTL_SECONDS` in [config.py](config.py).

### Object store

Backtest result CSVs are stored in an S3-compatible object store. In local development this is MinIO (started via `docker compose`). To switch to AWS S3 in production, remove `OBJECT_STORE_ENDPOINT` from your environment — the boto3 client will then use the standard AWS endpoint automatically. All other `OBJECT_STORE_*` variables remain the same shape.

## Configuration

All tuneable values are in [config.py](config.py):

| Setting | Default | Description |
|---|---|---|
| `BACKTEST_LOCK_TTL_SECONDS` | 10800 (3 h) | Distributed lock TTL; set above your longest expected backtest |
| `WORKER_QUEUE_TIMEOUT_SECONDS` | 5 | How long a worker blocks waiting for a queued task |
| `WORKER_SHUTDOWN_TIMEOUT_SECONDS` | 30.0 | Grace period for the worker to finish on server shutdown |
| `WORKER_CLEANUP_INTERVAL_SECONDS` | 900 (15 min) | How often the periodic stale-task cleanup runs |
